# EDU KIT

小学校向けWeb教材を、AIと人が同じ設計基盤から安全に作成・改修するためのハブです。

`edu-kit`は、共通資産をコピーして配る場所ではありません。学習目標から教材の構造を決め、必要な共通基盤を選び、正本の実装・公開カタログ・実在する画像や音のIDへ案内する「設計・接続・確認の入口」です。

## edu-kitと5つの共通基盤

TT-senseiの教材は、必要に応じて次の5つを組み合わせます。5つすべてを必ず使うわけではありません。

| 基盤 | 担当 | 教材との接続 |
| --- | --- | --- |
| [edu-components](https://github.com/TT-sensei/edu-components) | 出題、判定、進行、採点、保存、報酬などの動作・ロジック | 状態・イベント・学習フローの中心 |
| [edu-effects](https://github.com/TT-sensei/edu-effects) | 学習UI、正誤、進捗、カード、アニメーション、視覚演出 | componentsの状態変化を画面で伝える |
| [sounds-recipe-](https://github.com/TT-sensei/sounds-recipe-) | Web Audio APIによる教材用効果音 | 正解、操作、達成、解放などを音で補助する |
| [edu-assets](https://github.com/TT-sensei/edu-assets) | バッジ、コレクション、エレメントなどの画像 | 報酬、達成、テーマ、教材内の共通画像 |
| [navi-character-](https://github.com/TT-sensei/navi-character-) | ナビキャラ、学習シーン、背景、ファンタジー、モンスター | 開始、ヒント、励まし、達成、冒険などを補助する |

役割を混ぜないことが重要です。たとえば正解処理そのものは`edu-components`、正解したことを視覚的に伝えるのは`edu-effects`、短い正解音は`sounds-recipe-`、バッジ画像は`edu-assets`、ナビキャラの「できた！」の場面は`navi-character-`という分担にします。

教材固有の問題データ、正答、学習順序、画面文言、達成条件は各教材側に置きます。共通基盤に教材固有のルールを埋め込まないでください。

## 5基盤を使う標準フロー

```text
学習目標・学習行動を決める
          ↓
       edu-kit
  設計・保護・資産選定
          ↓
  ┌───────────────┐
  │ edu-components │ ← 出題・判定・状態・保存
  └───────┬───────┘
          │ EDU_EVENTS / 状態変化
     ┌────┼────┬────┐
     ↓    ↓    ↓    ↓
 effects sound assets navi
  視覚    音    報酬   案内・世界観
     └────┴────┴────┘
          ↓
       教材画面
          ↓
   VERIFY / REGRESSION
```

5基盤は「全部盛り」にするためのものではありません。学習上必要なものだけを使います。ナビキャラや音、演出が問題・観察・操作より目立つ場合は、減らすことを優先します。

## AI開発の基本線

AIは「いきなり書き換える」のではなく、次の6段階で作業します。

1. DISCOVER — 現状把握
2. PROTECT — 保護対象と影響範囲
3. DIAGNOSE — 原因特定と実装方針
4. IMPLEMENT — 小さく実装
5. VERIFY — 変更箇所の検証
6. REGRESSION — 回帰確認

既存教材では、問題・正答・判定・保存・学習順序・既存画像リンクを保護対象として扱います。不具合の原因が分からないまま全面書き換えで直したことにしません。実装したことではなく、確認できたことを完了条件にします。

## 教材設計の基本線

- 学習の入口を一目で分かるようにする。最初に選ぶ学習行動を明確にする。
- タブレット横向きの1画面を基本にする。問題・操作・現在地を優先し、カードや絵を大きくしすぎない。
- 子どもが止まらないようにする。ヒント、解説、答えを見る、再挑戦、次へ進むなど、学習上意味のある脱出口を用意する。
- シミュレーターは「条件を変える → 現象が変わる → 短く確かめる」を基本にする。
- できたことを残す。学習履歴、進捗、バッジ、記録などは教材固有の保存領域で管理し、リロード後も続きが分かるようにする。
- 補助要素は学習のそばに置く。ナビキャラ、演出、音、報酬は問題・観察・操作より前に出さない。
- Web画像は軽量WebPを優先する。原本とWeb配信用画像の役割を混ぜない。
- 実在しないものを推測しない。API、CSSクラス、音ID、画像URL、キャラクター名、バッジ名は正本と公開カタログで確認する。

## 5つの基盤を選ぶ基準

### edu-componentsを使うとき

出題、正誤判定、タイマー、コンボ、進行、保存、レベル、バッジ解放など、教材をまたいで再利用できる動作が必要な場合に使います。既存のManagerやQuestion系部品を先に確認し、同じ処理を教材内へ再実装しません。

### edu-effectsを使うとき

カード、ボタン、選択肢、正誤フィードバック、進捗、達成、テーマ、モーションなどの共通UIや視覚演出が必要な場合に使います。既存クラスを確認し、教材ごとに同じCSSを複製しません。`prefers-reduced-motion`でも学習の意味が伝わるようにします。

### sounds-recipe-を使うとき

正解、操作、コンボ、時間切れ、達成、バッジ、解放などに短い音を加える場合に使います。まず既存の音IDを探し、同じ用途の音を教材ごとに作りません。ミュートしても教材が成立することを前提にします。

### edu-assetsを使うとき

バッジ、コレクション、エレメントなどの共通画像が必要な場合に使います。原本とWeb版を区別し、Web教材では可能な限り`assets/web/`の軽量画像を使います。存在しないパスを推測しません。

### navi-character-を使うとき

開始、ヒント、励まし、再挑戦、達成、学習場面、冒険などをキャラクターで補助する場合に使います。通常の学習では通常版ナビキャラを優先し、ファンタジーキャラクターやモンスターは冒険・バトル型教材で使います。キャラクターのIDENTITY LOCKや実在する画像パスを守ります。

## 共通基盤どうしをつなぐ

共通基盤間の中心的な接続点は`EDU_EVENTS`です。教材固有のイベントや状態を勝手に共通基盤へ埋め込むのではなく、既存のイベント仕様を確認して接続します。

たとえば、子どもが正解した場合は次のように考えます。

```text
回答
 ↓
edu-components
 ├─ 正誤判定
 ├─ 進捗更新
 └─ EDU_EVENTS
      ├─ edu-effects → 正解フィードバック
      ├─ sounds-recipe- → correct系サウンド
      ├─ edu-assets → 条件達成時のバッジ
      └─ navi-character- → 必要ならナビキャラのcelebrating等
```

重要なのは、正解処理を5基盤それぞれが個別に判定しないことです。判定・状態の正本を`edu-components`側に置き、他の基盤はその結果を受けて補助的に動かします。

## 作業の順番

1. 学年・教科・単元・学習目標を確認する。
2. 新規作成か既存教材の改修かを判断する。
3. 既存の問題・正答・判定・保存・画像リンク・イベント接続を確認する。
4. DEVELOPMENT-PROTOCOL.mdに沿って、保護対象・影響範囲・実装方針を整理する。
5. 子どもが繰り返す学習行動と、1回の学習単位を決める。
6. 5基盤から必要なものだけを選ぶ。
7. 正本の実装と公開カタログで、API・クラス・イベント・音ID・画像パスを確認する。
8. まず学習骨格を作る。タブレット横向きの1画面で主要操作を確認する。
9. 必要な場合だけ、視覚演出・音・バッジ・ナビキャラを接続する。
10. 正解・不正解・つまずき・再挑戦・結果・ホーム復帰・リロードまで回帰確認する。
11. コンソールエラー、画像404、存在しないCSSクラス、存在しない音ID、イベント不整合を確認する。
12. [更新・検証ルール](MAINTENANCE.md)に沿って点検する。

## AIへの基本指示

~~~text
制作前に https://github.com/TT-sensei/edu-kit を起点として確認してください。
最初に DESIGN-PRINCIPLES.md、DEVELOPMENT-PROTOCOL.md、AI-GUIDE.md、該当する skills/*/SKILL.md を確認してください。

次に、必要な共通基盤を選びます。
- edu-components = 動作・ロジック・状態
- edu-effects = UI・CSS・視覚演出
- sounds-recipe- = サウンド
- edu-assets = バッジ・画像
- navi-character- = ナビキャラ・シーン・ファンタジー素材

既存教材では、編集前に問題データ・正答・判定・保存・画像リンク・イベント接続を確認し、保護対象と影響範囲を明記してください。
READMEだけで判断せず、各リポジトリの正本と公開カタログでAPI、CSSクラス、イベント、音ID、画像URLの実在を確認してください。

不具合修正では、再現→原因特定→最小修正→変更箇所の検証→回帰確認の順で進めてください。
判定や状態を複数の基盤で重複管理せず、edu-componentsを中心にして他の基盤を接続してください。

タブレット横向きの1画面を基準に、子どもが迷わず学び、止まっても再開できる導線を作ってください。
ナビキャラ、音、視覚演出、バッジは学習内容を補助するために使い、学習の主役にしないでください。

実装しただけで完成扱いにせず、基本フロー・保存・リロード・端末表示・画像読み込み・音再生・イベント・コンソールエラーまで確認してください。
~~~

## skillsの位置づけ

`skills/*/SKILL.md`は、Claude Code・CodexなどのAIエージェントが作業手順として直接読むための実行仕様です。自動読込に対応しないAIでも、AI-GUIDEと該当Skillを依頼文・チェックリストとして参照できます。

各Skillは「いつ使うか」「最初に確認するもの」「使用候補」「手順」「完了条件」を持ちます。複数該当する場合も必要なものだけを選び、最後にfinal-reviewを実行します。

## 整合性確認

Node.js 18以上で、外部パッケージを追加せずに実行できます。

~~~bash
node scripts/verify-repositories.mjs
~~~

5つの共通基盤の入口、ガイド、主要ファイル、`edu-effects`のCSS記載、`sounds-recipe-`の音レシピ、`edu-assets`の画像パス、`navi-character-`の画像パス、edu-kit内のSkill構造を確認します。詳細は[更新・検証ルール](MAINTENANCE.md)を参照してください。

## 実装の前提

- HTML / CSS / Vanilla JavaScript
- GitHub Pagesから直接動作する
- npm、ビルド、APIキー、外部DBを教材本体の前提にしない
- 新規教材の保存は教材固有namespaceを使い、既存教材の保存形式は理由なく変更しない
- localStorageを使う場合は、教材内で直接散在させず、原則としてStorageManagerに集約する
- `EDU_EVENTS`を共通資産間の接続点にする
- 問題データ、画面文言、正答、達成条件は教材側に置く
- タッチ、マウス、必要に応じてキーボードに対応する
- 長押しやドラッグだけを必須操作にしない
- `prefers-reduced-motion`でも学習の意味が伝わる
