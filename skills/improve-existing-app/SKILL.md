# Improve Existing App

## いつ使うか

既存教材の学習内容と動作を守りながら、UI、導線、演出、レスポンシブ等を改善するときに使う。

## 最初に確認するもの

1. DESIGN-PRINCIPLES.md
2. DEVELOPMENT-PROTOCOL.md
3. AI-GUIDE.md
4. 現在のソースと公開画面
5. 画面構成、問題データ、判定、進行、保存、画像リンク
6. ユーザーが触らないと指定した領域
7. 既存保存データの形式
8. 画像・CSS・外部モジュールの読み込み先

## 使用候補

- 改善対象に必要な共通資産だけ
- UI変更：edu-effects
- ロジック置換が明示的に必要な場合：edu-components
- ナビキャラ、音、報酬は別Skillも併用

## 必須プロトコル

DEVELOPMENT-PROTOCOL.mdの6段階を省略しない。

1. DISCOVER — 現状把握
2. PROTECT — 保護対象と影響範囲
3. DIAGNOSE — 原因特定と実装方針
4. IMPLEMENT — 小さく実装
5. VERIFY — 変更箇所の検証
6. REGRESSION — 回帰確認

## 手順

1. 壊してはいけない領域を保護対象として明文化する。
2. 公開画面とソースを照らし、実際に使われている入口・単元・画像・保存キーを特定する。
3. 問題データ・正答・判定ロジック・問題数・保存は、依頼に必要でない限り変更しない。
4. 改善対象、変更ファイル、直接影響、間接影響を整理する。
5. 不具合修正では、まず再現し、原因を特定してから修正する。
6. 原因不明のまま、関連ファイル全体を書き換えない。
7. 共通部品を導入する場合も既存挙動との互換性を優先する。
8. 全面書き換えをする場合も、画面・UI・演出・ロジック・データを分けて置き換える。
9. 実装後、今回変更した箇所を最短経路で検証する。
10. 開始画面の選択、学習、正解、不正解、つまずきからの脱出、結果、ホーム復帰を確認する。
11. 答えを見る機能を追加する場合は、正答・マスター達成と別の状態で保存する。
12. 既存保存データ、新規状態、リロード後の状態を確認する。
13. タブレット横向きの1画面で問題・観察・主要操作を確認する。
14. 画像リンク、文字切れ、白いちらつき、レイアウトシフト、コンソールエラーを確認する。
15. final-reviewを実行する。

## バグ修正時の追加ルール

- 「症状」と「原因」を分けて考える。
- 再現条件を確認する。
- 原因候補をコードと状態から絞る。
- 修正は原因に対して行う。
- 同じ原因が他の画面・モードにもないか確認する。
- 修正後、再現手順をもう一度通して直ったことを確認する。

## UI改善時の追加ルール

- 見た目だけの変更でも基本フローを壊していないか確認する。
- 問題・式・観察対象・主要操作を装飾より優先する。
- 余白を減らす場合、誤タップや可読性低下を起こさない。
- タブレット横向きで1画面に収まることを優先し、スマホは必要に応じて縦積みにする。

## 完了条件

- 保護対象を変更していない。
- 原因がある不具合は、原因を説明できる状態で修正している。
- 正解して進め、不正解や長い迷いでも停止しない。
- ヒント・解説・答えを見る・再挑戦など、必要な脱出口がある。
- ホーム復帰と再スタートができる。
- 問題数・正答・学習順序が意図せず変わっていない。
- 既存保存データとリロード後の状態が壊れていない。
- タッチとマウスで操作できる。
- 補助資産の失敗で学習本体が止まらない。
- 重大な回帰が0件。
- 確認していないことを「確認済み」と報告していない。
